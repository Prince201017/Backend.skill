# Advanced Backend Engineering & Security Skill (V2.2 DevilScanner-Hardened Standard)

## 1. Purpose & Non-Negotiable Engineering Rules

This master specification and its 16 modular reference files (`00`–`15`) define a security-first, technically verifiable TypeScript backend engineering standard. Every pattern, code implementation, and verification test across this library obeys these non-negotiable rules:

1. **Zero Trust for Client-Supplied Claims**: Never treat client-provided tenant IDs, user IDs, roles, boolean flags (`isAdmin`, `dualApprovalConfirmed`, `gatewayOidcVerified`), headers, webhook metadata (`claimedTenantId`), or broker event payloads as proof of authorization.
2. **Explicit Trust Boundaries, Threat Models & Limitations**: Every security control documents its trust boundary, threat model, enforcement location, failure behavior, and operational limitations (e.g., PostgreSQL RLS protects against missing `WHERE tenant_id` clauses under a `NOBYPASSRLS` role, NOT against SQL injection calling `set_config()` or compromised DB credentials).
3. **Authenticate & Authorize Before Establishing Database Context**: In multi-tenant PostgreSQL architectures (`withTenantTransaction`), verify at startup that the DB role has `rolsuper = false` and `rolbypassrls = false` (`verifyDatabaseRoleRlsEnforcement`), and never populate `app.current_tenant_id` before verifying the caller's cryptographic identity, active tenant status, active membership status (`status = 'ACTIVE'`), and required action permission inside the transaction.
4. **ReBAC Ownership != Administrative Authority & Intra-Tenant BOLA Defense**: Resource ownership (`owner` of an order, file, or project) grants only explicitly mapped owner actions and NEVER bypasses administrative or financial permission checks (`order:refund`, `ledger:export`, `member:invite`, or marking a BaaS project `'COMPLETED'`). File downloads (`authorizeApprovedFileDownload`) and cache hits (`getOrComputeAuthorizedCachedSingleFlight`) must enforce per-user instance authorization inside the tenant.
5. **Fenced Idempotency, Single-Transaction Maker-Checker & Reconciliation**: Mutating operations and payments enforce leased idempotency keys with `lockOwnerToken`, monotonic `fencingToken`, periodic lease renewal, conditional completion, and transition to `UNKNOWN_RECONCILIATION_REQUIRED` on ambiguous provider timeouts. Maker-Checker approvals execute state verification (including live Maker and Checker active membership), state transition, atomic balance deduction, and HMAC audit logging inside a **single ACID transaction**.
6. **Confused-Deputy & Prompt-Injection Defense for MCP Tools**: Mutating MCP tools (`executeMcpToolWithRuntimeAuthz`) enforce strict argument key allowlists (`allowedArgKeys`) and require a cryptographic Human-in-the-Loop confirmation token (`computeMcpUserConfirmationToken`) bound to `(userId, tenantId, toolName, canonicalArgs)`.
7. **Honest Verification Reporting**: Never claim a system is production-ready or that tests passed unless verified; distinguish executed in-process Node.js tests (`node:test`) from external-daemon integration tests (live PostgreSQL, ClamAV, Firebase Emulator).
